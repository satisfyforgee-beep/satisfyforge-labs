# SatisfyForge Service Scoping & Close Kit

Use after a prospect has replied, received a useful sample, and shown real interest. This is not a mass-outreach script and it is not permission to send unsolicited payment links.

## Rules

- Scope the buyer's actual problem before quoting custom work.
- Never invent revenue, lead volume, conversion rates, case studies, testimonials, urgency, scarcity or guaranteed ROI.
- Never tell a buyer a checkout/payment link is ready unless that exact link and amount were verified.
- Tool Vault KLjBb remains paused/unverified and is never used to collect service money.
- While direct service checkout links are unverified, use the Wix request form + written scope. A verified PayPal invoice/payment request may be used only when the exact recipient, amount and scope are confirmed.
- Third-party software/hosting costs are customer-funded in advance when unavoidable; SatisfyForge does not front them.
- Do not begin a large custom build before the agreed first payment/milestone is actually received.

## Fast qualification questions

Ask only what changes the scope:
1. Where do leads/inquiries currently arrive? Phone, form, Facebook, Instagram, Google, CRM, email, other?
2. What happens after a new inquiry arrives today?
3. What is the main leak: slow response, no follow-up, stale estimates, weak offer, inconsistent content, poor tracking, something else?
4. Who will use the system day to day?
5. What tools/accounts must the system work with?
6. What outcome would make the project clearly useful?

Do not demand financial numbers when a useful scope can be created without them.

# $1,500–$4,999 Custom Automation / Software

Do not quote from the website range alone. First produce a written scope with:
- exact workflow
- inputs/outputs
- accounts/integrations
- data/storage needs
- user roles
- external dependencies
- acceptance criteria
- milestone plan

Use milestone payments for work that cannot responsibly be delivered as one small fixed package.

## Suggested milestone structure

For a custom build, choose a structure that matches real work. Example only:
- Milestone 1 — discovery/spec + working skeleton
- Milestone 2 — core workflow
- Milestone 3 — integration/QA/handoff

Do not call a milestone paid until payment is actually received.

# Reply when a buyer says “How much?”

`Based on what you've described, I’d keep this at the smallest tier that actually solves the problem. I can scope it at $___ for [specific deliverables]. That would include [3–5 concrete items] and exclude [important exclusions]. If that scope works for you, I’ll put the exact deliverables in writing before any build starts.`

# Reply when a buyer says “Can you guarantee results?”

`I can guarantee the deliverables we agree to build; I can’t honestly guarantee revenue, bookings or conversion because those depend on your traffic, offer, response, sales process and market. The point of the scope is to make the system measurable so we can see what actually changes.`

# Reply when they want “everything”

`I can build toward the larger system, but I don't want to sell you a giant package before we know which part actually matters. I’d start with [smallest useful phase]. If that works and the data says the next phase is worth doing, we expand from there.`

# Ready-to-scope checklist

Before saying “ready for payment,” confirm:
- prospect/company identity is clear
- exact deliverables are written
- price is explicit
- revisions/support boundary is explicit
- external costs are identified
- target timeline is described as a target, not a guaranteed impossible deadline
- buyer has agreed to the scope
- exact payment method/link/invoice is verified

If the payment path is not verified yet, keep the scope ready and say payment setup is being finalized rather than improvising bank details or an unverified URL.
